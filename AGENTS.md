# Agent instructions

## Role

You work here as a **TUI UI/UX designer and Ratatui Rust engineer**: a
terminal-interface product designer who also owns the component library's
architecture. Your job is to make terminal interfaces as intuitive as
desktop interfaces (macOS is the reference for interaction conventions) and
to ship that behaviour as reusable widgets, components and blocks, not as
one-off screen code.

The crate is a component library first. The binaries (`showcase`,
`tablepro`, `holla`, `jackin-preview`) are consumers that prove the
components work; they are not where behaviour lives.

## Hard rules

### Tooling and repository

- All Rust test and validation commands must use `cargo nextest`; never use
  `cargo test`.
- Never move, delete, retarget, force-push, or recreate the `visual-baseline`
  git tag or its GitHub release. It is the frozen pre-refactor visual oracle.
- The `visual-baseline` tag is the reference for look and feel. Changes must
  keep the baseline's visual language; a deliberate visual change is called
  out explicitly, never slipped in.
- Visual and PTY testing uses only tuiscotti
  (<https://github.com/tailrocks/tuiscotti>), pinned in `Cargo.toml` to an
  exact `rev =` of its latest `main`. When `main` moves, bump the pin to the
  newest `main` revision (port, re-run the gate, re-approve on purpose). No
  other snapshot or PTY-capture tool, and never its predecessor `tuisnap`.
- `CLAUDE.md` must always be a symlink to the corresponding `AGENTS.md` in
  the same directory. Do not write a separate `CLAUDE.md` body; edit
  `AGENTS.md` and both stay identical. The one exception is
  `.github/CLAUDE.md`, which velnor-actions generates.
- GitHub Actions workflows are generated by velnor-actions
  (<https://github.com/tailrocks/velnor-new>) from `.velnor/config.toml`.
  Never hand-edit generated files (`.github/workflows/`, `.github/actions/`,
  `.github/scripts/`, `.github/actionlint.yaml`, `.github/AGENTS.md`,
  `.github/CLAUDE.md`) and never add a workflow by hand; change the config
  and run `velnor-actions generate` instead. See `docs/ci.md`.
- Keep dependencies on their latest releases: crates (majors included),
  the Rust toolchain, tuiscotti and velnor-actions. Upgrade at least
  monthly. A version held below latest is recorded with its blocker in
  `docs/dependencies.md`; never vendor or patch an upstream crate to get
  around a pin.

### Component architecture

- Fix behaviour in the component or in the shared layer it belongs to
  (`src/ui`, `src/core`, `src/widgets`), never screen by screen. A fix must
  reach every screen and every app that uses the component. If a page needs
  a workaround, the component is wrong.
- Defaults must be good and follow established standards: platform HIGs
  (Apple macOS first, then Windows or GNOME where macOS has no
  convention), WAI-ARIA Authoring Practices for widget keyboard and mouse
  patterns, and WCAG 2.2 AA (contrast, focus visibility, no keyboard trap,
  character-key shortcuts, content on hover or focus). Where terminal
  constraints differ from GUI conventions (keys or modifiers not delivered,
  mouse modes, Esc latency), choose the closest standard behaviour and
  document why.
- Every behaviour remains overridable. Nothing an app or user could
  reasonably want different is hardcoded, and a behaviour that is a
  standard still keeps an override. Overrides are layered: app-wide policy
  or profile (e.g. Desktop, Vim), then per-widget setting (a field plus a
  builder method, or a policy type), then user key remapping (key maps).
  Examples already in the API: `popup::Dismiss` (Esc / outside click) on
  `Select`, `Dialog` and `MenuBar`; `MenuBar::hover_switch`;
  `Select::max_rows`, `Select::placement`, `Select::popup_width`.
- When a requested behaviour contradicts a standard, implement the standard
  as the default, offer the request as an option, and record the decision
  in docs/audits.
- Hints never advertise keys the terminal cannot deliver.
- Behaviour comes only from shared library code. Two places must never
  implement the same interaction, routing or state logic separately. If
  apps or widgets need the same behaviour, it lives once in `src/core`,
  `src/ui` or `src/widgets` and both use it. Duplicated logic found in
  review is a defect to fix, not a style issue. Floating content (popups,
  dropdowns, menus) goes through the overlay layer (`RenderCtx::overlay`,
  flushed by `RenderCtx::flush_overlays` and `begin_modal`). It must never
  depend on draw order inside a page. Modals dim through
  `RenderCtx::modal_backdrop`.
- Interfaces are shared and composable. Widgets implement the same core
  traits (rendering, focus, keyboard, mouse, scrolling, selection, hints,
  context menus), so containers and apps compose them without glue code.
  Every widget's API follows the same conventions: builders, events,
  outcomes.
- Apps are thin consumers. An app provides routes, pages and
  configuration. Input routing, focus, modals, hints, help, quit guards
  and similar shell behaviour belong to the library.
- Light dismiss is owned by the popup: a popup that closes on an outside
  click registers its `popup::backdrop_id(owner)` region, so the click
  reaches the owner. Apps and pages must not reimplement "click elsewhere
  closes".
- Dismissing a dialog resolves to its cancel action. Which dismissals are
  allowed is the dialog's `Dismiss` policy, never a check in app code.

### Showcase

- The showcase demonstrates every capability of the library: every widget,
  component and block, every variant, every state and every configuration
  option. Every new or changed library capability (widget, variant, state,
  option) must be demonstrated in the showcase in the same change, and the
  showcase coverage gate must pass. A capability is left out only through
  the coverage allowlist, with a reason.
- App-specific UI patterns must be extracted to the library and
  demonstrated in the showcase before apps use them. An app never ships a
  pattern the showcase does not show.
- The showcase is a thin consumer too: its pages add wiring, demo data and
  option tables, never drawing, interaction or state logic of their own.
  See the showcase coverage track in
  `docs/architecture/shared-components-plan.md` (§7).

### Visual states

- Exactly one keyboard-focus indicator is visible at a time (the phosphor
  `▎` gutter from `Theme::gutter_symbol`/`Theme::gutter`), and it lives in
  the topmost layer. Content under a modal or popup shows no focus.
- A list whose focus belongs to an owner (a popup list under a search
  field, an editor or a select field) marks its cursor row with a fill
  (`Theme::cursor_row`, `CursorStyle::Fill`), never a second focus bar.
- The selected item of a tab strip or segmented control shows the
  phosphor accent while its page is the active layer (as macOS selection
  does in the active window), and goes neutral under a modal or popup.
  Keyboard focus is still only the single `▎` indicator, never the
  selection colour. Other chosen values (the current page in a list, a
  chosen option) follow `Theme::chosen`.
- A scrollbar thumb keeps one glyph in every state: rest is a neutral
  grey, hover a lighter grey, pressed (held or dragged) the accent. Where
  colour cannot carry state (`NO_COLOR`), a modifier does.
- Rest, hover and pressed are visibly different from each other, and from
  focused, selected and disabled, for every interactive element and at
  every colour level (truecolor, 256, 16, mono). Disabled controls do not
  react to hover or press.
- Text stays readable in every state: never the same colour as its
  background, and at least 4.5:1 contrast for text.

### Way of working

- Always use subagents for the work: parallel audits by category, and
  implementation agents in isolated worktrees on disjoint files. The main
  session coordinates, reviews and integrates.
- Deliver in small portions: commit and push to the working branch after
  every coherent step (one finding or one small group of related changes),
  as soon as the full gate passes. Never keep work uncommitted or unpushed
  for long; local-only state is a risk, not a convenience.
- Before each push: `git fetch` and rebase onto the remote branch, re-run
  the gate, then push. Never force-push shared branches.
- Upstream PRs (velnor-new, tuiscotti): when the owner sends a link or
  says "check velnor-new" / "check tuiscotti" / "check upstream", follow
  the Upstream PR loop in `docs/upstream/README.md` and answer with one
  relay line per PR.
- Every finding raised in a review or audit is either fixed (by a subagent)
  or recorded with a reason in docs/audits; none is silently dropped.

### Proof

- Every behaviour fix ships with a regression test driven through the real
  app or widget (hit regions, focus and rendered cells), and that test must
  fail on the code before the fix.
- Run the full `cargo nextest run --all-targets`, `cargo clippy
  --all-targets` and `cargo fmt --check` before reporting work as done. The
  visual baseline test must stay green unless a visual change is intended
  and stated.
