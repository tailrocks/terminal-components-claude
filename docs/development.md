# Development

## Toolchain and dependencies

The workspace pins Rust `1.98.1` in `rust-toolchain.toml` and uses edition 2024. Install the pinned compiler with the components used by the workspace checks, then fetch locked dependencies from the repository root:

```sh
rustup toolchain install 1.98.1 --profile minimal --component clippy --component rustfmt
cargo +1.98.1 fetch --locked
```

The workspace has shared Termrock crates, deterministic demo applications, conformance/testing tools, and the visibility publisher. CI also provisions `cargo-nextest`; `.github/workflows/ci.yml` is generated by the Velnor workflow.

## Run the applications

Launch one application at a time from the repository root; each command opens an interactive terminal UI:

```sh
cargo run -p showcase
cargo run -p jackin-preview
cargo run -p holla
cargo run -p tablepro
```

Jackin Preview, Holla, and TablePro support `--help`, for example `cargo run -p holla -- --help`. Showcase uses `--page`, `--theme`, `--color`, `--motion`, and `--frame`; its entry point does not provide a help screen. Run options and behavior are implemented in the corresponding app/UI crates.

## Checks

Run these from the repository root:

```sh
cargo fmt --all -- --check
cargo check --workspace --offline
cargo test --workspace --offline
cargo clippy --workspace --all-targets --offline -- -D warnings
```

The facade's headless example tests require its `testing` feature, as in `cargo test -p termrock --features testing --test ex01_button --offline`. The independently version-pinned capture qualification workflow is documented in [qualified capture](../tools/qualified-capture/README.md); its README is a hash-pinned tool input and must remain byte-identical to `pins.json`. A workspace check or test pass proves only the exercised compile-time and test behavior. It does not establish product readiness or parity with [the design reference](design.md).

## Generated visibility records

Root `STATUS.md` and `WORK_QUEUE.md` are generated publisher/test records, not product documentation or readiness claims. Tests consume the checked-in records as fixtures. The visibility publisher provides `python3 tools/visibility/status.py --check` and `python3 tools/visibility/queue.py check`; regeneration is an explicit data-maintenance operation, not part of editing documentation. The JSON task/source records remain the structured inputs.

## Source comments

Do not add comments to Rust code on `main`. Put implementation rationale and developer guidance in the appropriate documentation. Preserve required compiler attributes and documentation metadata; they are code, not comments. Keep unsafe-operation rationales in [SAFETY.md](../SAFETY.md) and link them to the unchanged operation.
