# CI

## How it is generated

All GitHub Actions configuration is generated by **velnor-actions**
([tailrocks/velnor-new](https://github.com/tailrocks/velnor-new)), pinned to
release **v0.1.9**. Inputs, all outside `.github/`:

- `.velnor/config.toml`: the only file to edit.
- `.velnor/release-manifest.json`: a byte-identical copy of the v0.1.9
  release manifest (per-target asset URL and SHA-256). CI downloads exactly
  that binary and checks its digest.
- Repository state velnor reads: `Cargo.toml`, `.config/nextest.toml`
  (selects the nextest `ci` profile), and `rustfmt.toml` (turns on the fmt
  step).

Outputs, owned by velnor and never hand-edited: everything under
`.github/workflows/`, plus `.github/actions/`, `.github/scripts/`,
`.github/actionlint.yaml`, `.github/velnor/`, `.github/AGENTS.md` and
`.github/CLAUDE.md` (a symlink to `AGENTS.md`, from `[agents] claude_md =
"symlink"`).
Each file starts with `# Generated by Velnor Actions 0.1.9`.

## Regenerate

Install the pinned binary from the
[v0.1.9 release](https://github.com/tailrocks/velnor-new/releases/tag/v0.1.9)
and check its SHA-256 against `.velnor/release-manifest.json`. Then:

```sh
velnor-actions plan       # what would be generated, writes nothing
velnor-actions generate   # rewrites the owned .github paths
```

Commit the config change and the regenerated files together. To upgrade,
replace the manifest with the new release's `release-manifest.json`, install
that binary and regenerate.

**Drift check:** the generated `Plan` job runs `velnor-actions generate
--output-dir` and `diff -r --brief .github` against it. A hand edit, a stale
regeneration, or any extra file in `.github/workflows/` fails CI.

## Jobs and triggers

`ci.yml` (workflow `CI`) runs on pull requests (opened, synchronize,
reopened, ready_for_review), on pushes to `design/interaction-polish`, and
in merge queues. Runner: `ubuntu-24.04`; tools through Mise.

**Rust in CI follows `rust-toolchain.toml`** (1.99.1 with clippy and
rustfmt). Since velnor 0.1.9 the generator reads the file, installs
`rust@<channel>` and exports no `RUSTUP_TOOLCHAIN`, so local and CI use the
same compiler and `rust-version` in `Cargo.toml` matches it. The channel
must be an exact `X.Y.Z` (or `X.Y.Z-<target>`): `stable` or `1.99` makes
`velnor-actions generate` fail with `invalid_rust_toolchain` (checked with
`generate --output-dir`). Without a toolchain file velnor would fall back to
its own default (still 1.98.1 in 0.1.9). Other tools use velnor's catalog
(cargo-nextest 0.9.148, actionlint 1.7.12, shellcheck 0.11.0, zizmor
1.30.1); `[tools]` in `.velnor/config.toml` can pin newer exact versions,
but velnor only checks their shape, so a pin that does not exist fails at
install time in CI, not at generate time.

| Job | What it runs |
|---|---|
| `Actionlint` | actionlint 1.7.12 + shellcheck on the workflows |
| `Plan` | drift check, affected-work plan for the PR |
| `Rust / junie-tui` | `cargo fmt --check`; `cargo clippy --all-targets -- -D warnings`; `cargo nextest list` (build); `cargo nextest run --profile ci`; `cargo doc --no-deps` |
| `Rust / xtask` | the same for the `xtask` crate |
| `Publish baseline` | push only: stores the plan result reused by later PRs. Still red on every push with 0.1.9: it checks the GitHub default branch (`main`), not the configured one (`docs/upstream/velnor-new-feedback.md` §9); not part of `Required` |
| `Required` | aggregates `Plan`, the Rust jobs and `Actionlint` |

No job runs `cargo test`: `[lib] doctest = false` in `Cargo.toml` removes the
doctest step (the doc example is mirrored by a unit test).

## Required checks

Configure in branch protection for `design/interaction-polish` (and `main`
when it uses the same config): require the single check **`Required`**. Do
not require the individual jobs; `Required` fails if any of them fails.

## Visual suites

`suites.yml` (workflow `Suites`) runs the visual tiers of
`docs/visual-testing/plan.md` §C1 as velnor nextest suites
(`[[stacks.rust.suites]]` in `.velnor/config.toml`). Each suite builds once
(`cargo nextest archive`), then runs its shards from the archive with
`--partition hash:<k>/<n> --profile <tier> --run-ignored only`.

| Suite | Profile | Shards | Timeout | Artifact |
|---|---|---|---|---|
| `visual-smoke` | `smoke` | 2 | 30 min | `visual-smoke-<k>` on failure: `target/tuiscotti/{actual,expected,diff}` |
| `visual-full` | `full` | 12 | 60 min | `visual-full-<k>` on failure, same paths |
| `visual-narrow` | `narrow` | 2 | 60 min | `visual-narrow-<k>` on failure, same paths |
| `visual-capture` | `capture` | 12 | 60 min | `visual-capture-<k>` always: `target/tuiscotti/actual` |

All run with 4 test threads (the 4-vCPU runner, plan §C3) and keep
artifacts 14 days.

**Every tier is manual until oracle v0 (plan T18).** Run one from the
Actions tab (`Suites`, "Run workflow") with input `tier` (`smoke`, `full`,
`narrow`, `capture`) and an optional nextest filterset `filter`, for
example `test(/^holla::/)`. velnor suggested `visual-smoke` as required on
PR and push and `visual-full`/`visual-narrow` nightly. Before T18 most
scenarios skip, and the re-approved pilot drifts with every UI change, so a
required smoke check would go red on unrelated work and a nightly run would
be red every night. After T18: give `visual-smoke` `triggers =
["pull_request", "push", "workflow_dispatch"]` and `required = true` (it
joins `Required`, so branch protection still requires only `Required`).
Give `visual-full` and `visual-narrow` `"schedule"` with `schedule = ["0 2
* * *"]`.

- **`capture` is its own nextest profile** (full plus narrow, see
  `.config/nextest.toml`) with `VISUAL_FULL=1` and `allow_failure = true`,
  so it also captures scenarios that are still pending and never fails the
  run. It uploads the whole `actual/` tree on every run (plan §D, E2: the
  oracle-candidate input to `cargo xtask visual import`).
- **No `report` path.** tuiscotti writes `actual/`, `expected/` and `diff/`
  under `target/tuiscotti/`.
- `[test_sharding]` stays unset. The required `Rust / junie-tui` run is
  small and does not need partitions.
