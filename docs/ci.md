# CI

## How it is generated

All GitHub Actions configuration is generated by **velnor-actions**
([tailrocks/velnor-new](https://github.com/tailrocks/velnor-new)), pinned to
release **v0.1.8**. Inputs, all outside `.github/`:

- `.velnor/config.toml`: the only file to edit.
- `.velnor/release-manifest.json`: a byte-identical copy of the v0.1.8
  release manifest (per-target asset URL and SHA-256). CI downloads exactly
  that binary and checks its digest.
- Repository state velnor reads: `Cargo.toml`, `.config/nextest.toml`
  (selects the nextest `ci` profile), and `rustfmt.toml` (turns on the fmt
  step).

Outputs, owned by velnor and never hand-edited: everything under
`.github/workflows/`, plus `.github/actions/`, `.github/scripts/`,
`.github/actionlint.yaml`, `.github/AGENTS.md` and `.github/CLAUDE.md`.
Each file starts with `# Generated by Velnor Actions 0.1.8`.

## Regenerate

Install the pinned binary from the
[v0.1.8 release](https://github.com/tailrocks/velnor-new/releases/tag/v0.1.8)
and check its SHA-256 against `.velnor/release-manifest.json`. Then:

```sh
velnor-actions plan       # what would be generated, writes nothing
velnor-actions generate   # rewrites the owned .github paths
```

Commit the config change and the regenerated files together. To upgrade,
replace the manifest with the new release's `release-manifest.json`, install
that binary and regenerate.

**Drift check:** the generated `Plan` job runs `velnor-actions generate
--output-dir` and `diff -r --brief .github` against it. A hand edit, a stale
regeneration, or any extra file in `.github/workflows/` fails CI.

## Jobs and triggers

`ci.yml` (workflow `CI`) runs on pull requests (opened, synchronize,
reopened, ready_for_review), on pushes to `design/interaction-polish`, and
in merge queues. Runner: `ubuntu-24.04`; toolchain Rust 1.98.1 and
cargo-nextest 0.9.148 through Mise.

The Rust version in CI is velnor's own pin, not ours: velnor 0.1.8
hardcodes `RUST_VERSION = "1.98.1"` (`crates/velnor-actions-mise/src/catalog.rs:50`)
and exports `RUSTUP_TOOLCHAIN: 1.98.1` on every job, so CI ignores
`rust-toolchain.toml` and a repository `mise.toml` (both checked with
`velnor-actions generate --output-dir`). Local development follows
`rust-toolchain.toml` (latest stable, see `docs/dependencies.md`), while
`rust-version` in `Cargo.toml` stays at the CI toolchain so CI still builds
and clippy's `incompatible_msrv` flags std APIs newer than CI. Run
`RUSTUP_TOOLCHAIN=1.98.1 cargo clippy --workspace --all-targets -- -D warnings`
before pushing to mirror CI. Raise both once a velnor release pins a newer
Rust.

| Job | What it runs |
|---|---|
| `Actionlint` | actionlint 1.7.12 + shellcheck on the workflows |
| `Plan` | drift check, affected-work plan for the PR |
| `Rust / junie-tui` | `cargo fmt --check`; `cargo clippy --all-targets -- -D warnings`; `cargo nextest list` (build); `cargo nextest run --profile ci`; `cargo doc --no-deps` |
| `Publish baseline` | push only: stores the plan result reused by later PRs. Red on every push on 0.1.8: it checks the GitHub default branch (`main`), not the configured one (`docs/upstream/velnor-new-feedback.md` §9); not part of `Required` |
| `Required` | aggregates `Plan`, `Rust / junie-tui` and `Actionlint` |

No job runs `cargo test`: `[lib] doctest = false` in `Cargo.toml` removes the
doctest step (the doc example is mirrored by a unit test).

## Required checks

Configure in branch protection for `design/interaction-polish` (and `main`
when it uses the same config): require the single check **`Required`**. Do
not require the individual jobs; `Required` fails if any of them fails.

## Gaps: visual jobs from the plan

`docs/visual-testing/plan.md` §D plans a PR smoke visual job (2 nextest
partitions), a nightly full matrix (12 partitions), a manual `capture` job
and `target/tuiscotti` artifact upload on failure. velnor-actions 0.1.8
cannot express these:

- no `schedule` or `workflow_dispatch` triggers, and no inputs;
- no artifact upload for repository paths;
- partitions only for the native nextest step (`[test_sharding]`), bounded
  by `[resources] test_process_budget`;
- custom jobs (`[[checks]]`) are Mise tasks that need fully qualified tool
  pins, and still run only on PR/push.

A hand-written workflow is not an option either: velnor owns all of
`.github/workflows/`, retires files it did not emit, and the drift check
fails on them.

Until upstream supports these, run the visual tiers locally
(`docs/visual-testing/`). The smallest step that velnor already supports is
folding the smoke tier into the required run. The change is prepared and
disabled, with the toggle documented in place:

1. `.velnor/config.toml`: `run_ignored = "all"`.
2. `.config/nextest.toml`: uncomment the `[profile.ci]` `default-filter`
   (every non-ignored test plus the smoke tier; the perf measurements, the
   full and narrow tiers stay out) and the 4-slot `pty-ci` override.
3. `velnor-actions generate`, commit config and regenerated files together.

Enable it only after oracle v0 (plan T18): until every scenario is
re-approved on tuiscotti from an ubuntu-24.04 capture, the required check
would either skip most scenarios or go red on unrelated UI work.

Keep `[test_sharding] default_shards = 1`. velnor 0.1.8 renders `N` shards
as `N` steps in the same job, each running the identical `cargo nextest run
--profile ci …` command without `--partition`, so extra shards repeat the
run instead of splitting it (checked with `velnor-actions generate
--output-dir`). Real partitions (`--partition hash:k/n`, see
`docs/visual-testing/README.md`), nightly, manual capture and artifacts need
an upstream velnor-new change.

Also generated, against the repo rule: velnor writes `.github/CLAUDE.md` as
a regular file containing `@AGENTS.md`, not a symlink. Replacing it with a
symlink would fail the drift check, so it stays until upstream changes.

## Prepared: velnor 0.1.9

velnor-new [#155](https://github.com/tailrocks/velnor-new/pull/155) is
merged to velnor `main` (`e34cfb8`). It covers every gap above and
`docs/upstream/velnor-new-feedback.md` §8: named nextest suites with real
`--partition` matrices, `schedule` and `workflow_dispatch` triggers with
inputs, artifact uploads, `Required` membership, `[agents] claude_md =
"symlink"`, and CI that honours `rust-toolchain.toml`. We verified it with a
build from `main` (see the tracker in the feedback file). It is **not
adopted yet**, because no release is tagged. A release binary checks its own
SHA-256 against `.velnor/release-manifest.json`
(`release_manifest_binary_mismatch`), and the generated CI downloads the
binary from the manifest's release URLs, so an untagged commit cannot be
pinned. When `v0.1.9` is tagged:

1. Replace `.velnor/release-manifest.json` with the release's manifest and
   install that binary (`docs/dependencies.md`).
2. In `.velnor/config.toml`: delete the commented `[test_sharding]` block
   and the "VISUAL SMOKE TOGGLE" comment (both superseded by suites), add
   `[agents] claude_md = "symlink"`, and append the suites below.
3. In `.config/nextest.toml`: delete the commented `[profile.ci]` smoke
   toggle. The `capture` profile already exists.
4. Run `velnor-actions generate`. New outputs: `.github/workflows/suites.yml`,
   `.github/velnor/task-execution-manifest-v1.json` and
   `.github/actions/declared-task-0/` (the last two come from velnor #153/#154).
   Remove the `.github/CLAUDE.md` exception from `AGENTS.md` and from this file.
5. CI now runs Rust 1.99.1 from `rust-toolchain.toml`. Raise `rust-version` to
   `1.99` in `Cargo.toml` and `xtask/Cargo.toml`. Delete the
   `RUSTUP_TOOLCHAIN=1.98.1` clippy instruction here and in
   `docs/dependencies.md`.

Suites to append. This config generates cleanly with the `e34cfb8` build,
and actionlint and zizmor (pedantic) report no findings on `suites.yml`:

```toml
[workflow.dispatch.inputs.tier]
type = "choice"
description = "Visual tier (docs/visual-testing/plan.md C1)"
default = "smoke"
options = ["smoke", "full", "narrow", "capture"]

[workflow.dispatch.inputs.filter]
type = "string"
description = "Optional nextest filterset, for example test(/^holla::/)"

[[stacks.rust.suites]]
id = "visual-smoke"
profile = "smoke"
run_ignored = "only"
partitions = 2
build = "archive"
timeout_minutes = 30
test_threads = 4
triggers = ["workflow_dispatch"]
dispatch_inputs = { tier = ["smoke"] }
filter_input = "filter"
artifacts = [{ name = "visual-smoke-{shard}", paths = ["target/tuiscotti/actual", "target/tuiscotti/expected", "target/tuiscotti/diff"], when = "failure", retention_days = 14 }]

# visual-full: as visual-smoke with profile = "full", partitions = 12,
# timeout_minutes = 60, tier = ["full"], artifact "visual-full-{shard}".
# visual-narrow: profile = "narrow", partitions = 2, timeout_minutes = 60,
# tier = ["narrow"], artifact "visual-narrow-{shard}".

[[stacks.rust.suites]]
id = "visual-capture"
profile = "capture"
run_ignored = "only"
partitions = 12
build = "archive"
timeout_minutes = 60
test_threads = 4
triggers = ["workflow_dispatch"]
allow_failure = true
env = { VISUAL_FULL = "1" }
dispatch_inputs = { tier = ["capture"] }
filter_input = "filter"
artifacts = [{ name = "visual-capture-{shard}", paths = ["target/tuiscotti/actual"], when = "always", retention_days = 14 }]
```

How this differs from the configuration velnor suggested:

- **Every tier is manual until oracle v0 (plan T18).** velnor suggested
  `visual-smoke` as required on PR and push, and `visual-full` and
  `visual-narrow` nightly. Before T18 most scenarios skip, and the
  re-approved pilot drifts with every UI change. A required smoke check would
  then go red on unrelated work, and a nightly run would be red every night.
  After T18: give `visual-smoke` `triggers = ["pull_request", "push",
  "workflow_dispatch"]` and `required = true` (it joins `Required`, so branch
  protection still requires only `Required`). Give `visual-full` and
  `visual-narrow` `"schedule"` with `schedule = ["0 2 * * *"]`.
- **`capture` is its own nextest profile** (full plus narrow, see
  `.config/nextest.toml`) with `VISUAL_FULL=1`, so it also captures scenarios
  that are still pending. It uploads the whole `actual/` tree on every run
  (plan §D, E2: the oracle-candidate input to `cargo xtask visual import`).
- **No `report` path.** tuiscotti writes `actual/`, `expected/` and `diff/`
  under `target/tuiscotti/`. `test_threads = 4` matches the 4-vCPU runner
  (plan §C3).
- `[test_sharding]` stays unset. The required `Rust / junie-tui` run is small
  and does not need partitions.
