# Owned fresh-plan create and verify lifecycle

This increment adds opt-in `--owned-lifecycle` and `--owned-budget` handling to `fresh-plan` and `verify-fresh-plan`. Each owned command creates one `PrepareExecution` scope and shares it across path resolution, frozen-source checks, reviewed cohort checks, live-source verification, tool observation, Nextest inventory, plan hashing, immutable plan publication, and flushed success output. Existing calls without the new flags retain their legacy behavior.

Owned plans record the configured work budget as `timeout_seconds_per_advance`. The owned default is 200 seconds, with the existing 15-second cleanup reserve, so it no longer seals the former 225-second advance allowance. Legacy plans keep the 225-second value. Owned verification requires the supplied work budget to match the sealed advance budget. `--owned-budget` without `--owned-lifecycle` fails, including when explicitly set to the normal 200-second default.

The plan reader, inventory transforms, source and tool hashes, and plan writer now accept the shared work check. Publication checks both sides of the immutable hard link and directory sync. A failure after publication leaves the immutable plan in place and returns an error without printing success. Final success output is flushed before the last cancellation/deadline check.

Verification on the synthetic runner fixtures: 12 focused fresh-plan tests passed, including real `PrepareExecution` child termination, hash-loop deadline, chunked-write deadline, immutable post-publication deadline, output cancellation, budget matching, and CLI propagation. The complete `python3 -m unittest tools.test_frozen_baseline` suite passed 117 tests. `py_compile` passed. No live cohort plan, run key, capture, replay, ordinary check, or candidate comparison was created or run.

This increment does not complete the fresh-run initialization/verification, owned advance, ordinal guard, ordinary phase, or complete receipt lifecycle. Do not create a live plan yet. The final runner must still receive independent review after all lifecycle source and tests are integrated; stage 3 must then verify the exact final runner before any stage 4 plan can seal its hash.

## Independent P1 follow-up

The independent review at commit `17abfae6e3cafddeaea71ba7a6aea5df1499fdfa` found two bounded-work gaps: `prepare-live --owned-lifecycle` resolved paths before creating `PrepareExecution` and printed success after leaving its scope; and fresh-plan publication could leave an immutable plan without a returned creation digest. This follow-up closes those boundaries without changing legacy command defaults.

Owned `prepare-live` now places path resolution, option checks, source verification, live-source preparation, JSON serialization, flushed output, and the post-output cancellation/deadline check inside one `PrepareExecution`. It checks the work budget before and after path resolution and source verification. The no-flag legacy path retains its prior output behavior. Synthetic CLI regressions cover deadline and SIGTERM during path resolution and after final output flush.

Owned `fresh-plan` now requires explicit `--creation-commitment-path` and `--pending-receipt-path` values outside the plan root. It serializes the exact plan bytes, durably and exclusively publishes the immutable creation commitment, then durably and exclusively publishes a canonical pending receipt containing the commitment digest and exact plan identity. Both files are flushed and fsynced, and their parent directories are fsynced before the plan link is attempted. Stdout is a supplementary notification; the plan cannot be linked until the durable receipt path exists and has been verified after publication. The caller must pin the commitment SHA-256 outside the plan root. The command does not claim atomicity across the commitment, receipt, plan, or stdout. If any persistence step fails, it does not publish the plan and preserves already-published files for diagnosis.

The creation commitment and durable receipt also pin the caller's absolute lexical root pathname, resolved canonical pathname, device, and inode. Owned creation checks this root binding around path resolution, before publication, and after final reads/output. Recovery rejects a root symlink or replaced directory, opens the canonical root component-by-component without following links, reads the plan relative to that directory descriptor, and checks the caller pathname/identity again after the read. These are bounded before/after checks and descriptor-relative plan reads; they do not claim universal protection against a privileged actor that can swap and restore path components between checks.

`recover-fresh-plan` requires the caller-pinned `--expected-commitment-sha256` and explicit `--pending-receipt-path`; it safely reads the unchanged regular files, checks the durable receipt and root identity against the pinned commitment and exact plan identity, validates the commitment against the full immutable plan bytes and plan self-digest, and returns only `creation-anchor-recovered` with `verified=false`. The normal `verify-fresh-plan --expected-plan-sha256` path remains mandatory and revalidates the fixed source, cohort, live source, tool observation, and complete inventory. A missing receipt, receipt/commitment mismatch, replaced root pathname or directory, missing plan, replaced commitment, unsafe file, digest mismatch, or plan collision does not recover a digest or authorize later phases. Existing artifacts are preserved for diagnosis.

The durable pending receipt and recovery record are not approval, source verification, key material, run initialization, capture, replay, ordinary-test evidence, candidate comparison, or product acceptance. The caller still must retain the commitment digest in a separate trusted record to recover after interruption. A matching durable receipt and plan only restore the original creation anchor; full verification remains mandatory.

Real temporary-directory regressions cover final-path symlink replacement, replacement with a different directory inode, replacement during descriptor-relative plan reading, and path replacement during creation/linking (which leaves only the pending output and returns no success record). Durable-receipt fault tests continue to cover file/directory fsync failures, SIGTERM/deadline during fsync, collisions, unsafe/replaced receipts, and successful recovery. All tests use synthetic fixture data; no real plan, key, capture, replay, ordinary check, or candidate run was created or executed. The remaining lifecycle ownership gaps listed in the previous section remain pending and no plan should be sealed until independent final-source admission.

## Owned prepared-run initialization

Git metadata probes now use the existing anchored broker when an execution context is supplied. The key remains an external mode-0600 file; its bytes are never included in logs, error records, child environment, or output.

Before key creation, the owned path validates the immutable plan evidence, root binding, key destination exclusion from protected roots, and Git metadata. After the unique run root is created, failures preserve a nonsecret `init-failure.json` marker. It reports only the plan, stage, error, and whether key bytes may exist. Verification refuses a run root containing that marker. It never deletes an orphan key or an existing run root. Failures during the real owned child deadline, handled SIGTERM, and root replacement are covered before key creation; manifest-publication failure preserves the marker while the private test key remains confined to a temporary fixture.

This increment is limited to init ownership. `fresh-run-verify`, deadline-owned advance, required ordinal/phase guards, complete ordinary-check phases, and final lifecycle review remain pending. No live plan, key, run, capture, replay, ordinary check, or candidate comparison was created; only short-lived key files in synthetic temporary unit-test fixtures were used. ## Independent init failure-marker correction

The independent review of commit `014d371620c362a3b455671d18a0c20c97844ecb` found that, after a manifest write and root replacement, owned initialization could follow the replaced pathname while writing its failure marker. Failure-marker publication now uses a directory descriptor opened for the created run directory and pinned to its device/inode. Before marker creation, the code rechecks the caller-pinned plan-root and run-directory identities; publication is relative to the original descriptor, never a new lookup through the replacement pathname. If identity is already lost, it fails closed without publishing a marker. The descriptor is checked around the durable write and always closed.

The real-filesystem regression writes a synthetic manifest, replaces the original root pathname with a fresh directory containing a sentinel, and asserts the replacement tree remains unchanged, no marker appears at either replacement or moved path, the original manifest remains preserved, and no success output appears. The existing valid-root manifest-failure test still requires the nonsecret failure marker. This correction is a narrow init recovery fix: advance/chunk ownership, required phase+ordinal guards, ordinary checks, and independent review of the resulting commit remain pending; no plan may be sealed from this partial runner.

An independent re-review of that correction found an earlier mkdir race: replacing the root immediately before `run_root.mkdir(parents=True)` created `fresh-runs/<plan_id>` inside the replacement. Owned init now opens the pinned plan root without following symlink components and creates/opens both `fresh-runs` and the unique plan directory through descriptor-relative `mkdir`/`open` operations, with no-follow checks, ownership/mode validation, parent fsyncs, and root-identity checks around each boundary. Manifest publication is also relative to the retained run-directory descriptor; marker publication remains anchored there. Real-filesystem regressions swap the pathname exactly before the relative plan-directory mkdir and reject a symlinked preexisting `fresh-runs` directory; they assert the replacement root and symlink target stay unchanged, no key or manifest is created, and no success output appears. Only the displaced original root receives an empty run directory in the swap case; no write is redirected through a replacement pathname.

Validation after the mkdir-boundary correction: `python3 -m unittest tools.test_frozen_baseline` passed 146 tests with 0 skips in 24.640 seconds; `python3 -m py_compile tools/frozen_baseline.py tools/test_frozen_baseline.py` and `git diff --check` passed. The two new regressions use synthetic temporary roots and keys only; no operational plan or application command was run.

## Independent nested-directory identity correction (pending review)

The independent review of `489beb371a611461c7f9a9ab0012710d5612643b` found that the run directory descriptor correctly kept the manifest in the original directory, but the initializer did not bind the `fresh-runs` parent identity or recheck the selected run-directory identity before success serialization/output. Replacing either nested path could therefore produce a success record whose `run_root` named a replacement directory without the manifest. Initialization now binds both directory identities from descriptor-relative creation and checks the root, parent, and run path chain before and after manifest publication, around success serialization, immediately before output, after flush, and before failure-marker publication. Lost identity fails closed without writing into the replacement path; the manifest remains in the displaced original directory for diagnosis.

Three real-filesystem fault probes replace the selected run directory after manifest publication, replace its `fresh-runs` parent after manifest publication, and replace the run directory immediately before success serialization. Each asserts that the replacement tree remains unchanged, the original manifest remains preserved in the displaced directory, and no success output is emitted.
