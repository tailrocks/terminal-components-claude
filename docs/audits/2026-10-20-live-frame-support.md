# Live frozen CLI frame support

The standalone helper at `tools/frozen-cli-frame-support/src/lib.rs` is intended to be copied into the frozen visual harness as a module. Its three explicit phases are `baseline-capture`, `baseline-check`, and `candidate-check`, configured through `TERMROCK_PAIR_PHASE`, `TERMROCK_PAIR_EXPECTED_ROOT`, and `TERMROCK_PAIR_RECEIPT_ROOT`. No variables means legacy frozen checks continue. Partial or invalid configuration fails closed.

Capture checks an existing frozen `.ansi` expectation through tuiscotti's strict `AnsiCursor` gate before writing a new runtime expectation with `create_new`; it never edits the frozen expectation. Replay and candidate phases check only the runtime expectation store with the same pinned profile, vendored faces, artifact set, and exact threshold. Every successful registered gate writes `{receipt_root}/{sha256(case_id)}/checkpoint-{ordinal:08}-{identity}.json` with exact JSON keys `case_id`, `ordinal`, `logical_name`, and `sha256` of canonical ANSI including cursor state. Runtime expectations use `checkpoint-{ordinal:08}-{identity}.ansi`. The 64-character lowercase identity is SHA-256 over `termrock-paired-checkpoint-v1\0`, full UTF-8 case ID, NUL, big-endian u64 ordinal, NUL, and full UTF-8 logical gate name. Receipts retain the full identity fields; bounded names remain below common filesystem component limits even for long scenario and gate names. Before any store operation, canonical future paths reject overlapping roots and validate every concrete approval, sidecar, actual, diff, expected, and receipt path; symlink descendants and multiply linked write destinations fail before reads or writes. Tuiscotti's expected-sidecar cleanup is redirected to a dedicated scratch root so original snapshots and runtime expectations remain unchanged.

The helper's TLS recorder resets at each `begin_case`, so parallel test threads keep independent case and ordinal state. The runner remains responsible for requiring at least one receipt per successful scenario and matching the complete checkpoint-key inventory across all three phases. This proves registered visual checkpoints only; it does not cover intermediate frames that never reach the central gate.

Validation uses the standalone crate so its files can be copied directly into a frozen harness without depending on either root workspace layout. Focused tests cover configuration fail-closed behavior, untouched originals, existing-original conflicts, canonical capture and receipts, replay mismatch, duplicate prevention, and checkpoint identity.
