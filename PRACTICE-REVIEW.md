# Practice review: test and comment rules

Date: 26 October 2026.

## Purpose

This review records which rules Termrock adopts from two source changes.
It does not approve either pull request or claim a full code review.

## Review method and limits

The review checked pinned commit metadata, root agent rules, changed-file lists, and selected review comments.
It did not read either complete pull request diff.
It did not inspect every changed file or every review thread.
The [Velnor pull request](https://github.com/tailrocks/velnor-new/pull/391) listed about 2,900 changed files.
The Jackin file view was paginated and truncated.
This review did not run Rust tests or verify every proposed fix.

The Velnor policy file was read at the requested commit.
A later file-list request showed a different Velnor head.
The findings below apply to the pinned policy and sampled review snapshot.
They do not describe every change at the later head.
The Jackin review snapshot included current and outdated unresolved threads.
An outdated thread does not prove that its original risk was corrected.

## Adopted rules

| Rule | Termrock policy | Limit of the source claim |
| --- | --- | --- |
| Plan tests first | Review an architecture plan and each task test plan before writing tests. | Google supports early testability review. Termrock requires a specific independent review gate. |
| Test observed behavior | Use public paths and assert resulting behavior. | This is a project choice for Termrock acceptance, not a rule for every codebase. |
| Avoid mirror tests | Do not copy production logic or assert call sequences as the main proof. | Google describes change-detector tests as low-value because they follow implementation changes. |
| Avoid owned-code mocks | Run owned production code. Use a double only at a justified external I/O boundary. | Google recommends real dependencies first, then fakes, then mocks when needed. Termrock sets a stricter owned-code rule. |
| Prove red and green | Show the intended test fail on a realistic defect and pass on the fixed candidate. | SWE-bench records fail-to-pass and pass-to-pass cases separately. This does not validate any Termrock test by itself. |
| Keep tests deterministic | Control time, data, files, and external services. Do not use uncontrolled live network. | Playwright describes isolation and controlled network routes. Its examples do not make every double faithful. |
| Bind each case to an outcome | Record the requirement, scenario inputs, expected result, case ID, and source SHA. | Termrock uses this local acceptance rule to make each result traceable. |
| Fix structural causes | Explain why architecture allowed an escaped issue. Prefer a fix to the enabling condition and record a deferred root cause. | Termrock keeps its existing architecture and review policy. |
| Reject empty evidence | A command with zero selected cases is `NOT VERIFIED`. | This is a Termrock acceptance rule. An empty lane cannot prove behavior. |
| Keep comments functional | Remove nonfunctional source comments. Keep legal, parser, linter, command-help, and generator-required text. | The pinned changes enumerate tool-required exceptions. Termrock adds a scoped policy for unsafe lint conflicts. |

The full T37 test cleanup is temporary.
Termrock will add reviewed tests after T38 approves their architecture.
The continuing comment rule permits required tool input and generated bytes.
It does not permit explanatory, TODO, or `SAFETY` comments in source code.

## Project-specific limits

Termrock adopts the shared test-planning, integration-first, red-green, determinism, and comment rules.
Source inspection establishes actual behavior. Approved contracts establish required behavior.
Comments do not prove either behavior or requirements.
The T37 migration must leave no active test-only files, fixtures, filters, or citations.
This cleanup rule does not extend to unrelated public APIs or production behavior.
It does not adopt another repository's broad API migration, research-project stance, or unsafe-code permission.
Termrock keeps its approved API contracts and safety limits.
Re-fetch every pull request review and comment at the exact candidate head.
Disposition each current finding with evidence and keep unresolved findings visible.
Use current user authorization before any external reply, push, merge, or release.

## Research references

These sources support selected test practices.
They do not establish a single consensus for AI-assisted software development.

- Google's [Inquiry Method for Test Planning](https://testing.googleblog.com/2016/06/the-inquiry-method-for-test-planning.html) asks teams to consider testability during design.
- Google's [Change-Detector Tests](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html) explains why tests that repeat implementation details do not prove behavior.
- Google's [Test Fidelity article](https://testing.googleblog.com/2024/02/increase-test-fidelity-by-avoiding-mocks.html) recommends real dependencies when practical, then fakes, then mocks when needed.
- Google's [Coverage Best Practices](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html) describes coverage as an indirect measure and says no single percentage fits every product.
- Playwright's [Best Practices](https://playwright.dev/docs/best-practices) recommends user-visible behavior and isolated tests. Its [API mocking guide](https://playwright.dev/docs/mock) shows controlled network substitutes.
- Anthropic's [agent evaluation guide](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) defines tasks, success criteria, graders, and final outcomes for agent evaluations.
- The SWE-bench [harness reference](https://www.swebench.com/SWE-bench/api/harness/) records fail-to-pass and pass-to-pass results as separate measures.

These sources inform Termrock's choices.
Termrock's no-owned-mocks rule, T37 cleanup, and independent review gates remain local requirements.
