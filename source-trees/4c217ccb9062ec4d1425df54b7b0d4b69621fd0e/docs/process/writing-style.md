# Technical writing rules

Use ASD-STE100 Simplified Technical English as the writing reference.
Use the authorized project skill or standard when available.
Do not copy an unverified rules summary as the complete standard.

Use active voice and direct instructions.
Write one instruction per sentence.
Use short procedural sentences, with a project target of 20 words maximum.
Use short descriptive sentences, with a project target of 25 words maximum.
Keep one topic in each paragraph.
Keep code identifiers and exact visible baseline text unchanged.

Use the same term for the same concept.
Do not call an import an adoption proof.
Do not call stored-data integrity live parity.
Do not call a target API an implemented API.

## Project terms

| Term | Meaning |
| --- | --- |
| component | A reusable unit that owns a declared visual and interaction contract. |
| composition | A view made from components and public layout helpers. |
| preview | One of the four UI applications that demonstrates the library. |
| oracle | An immutable reference used to define expected observations. |
| checkpoint | One identified observation after a defined event/time step. |
| admission | Independent acceptance of a reference artifact generation. |
| ownership proof | Evidence that the declared component produced the output and interaction. |
| parity | Equality under the explicitly declared visual or semantic comparison. |
| review subject | The exact parent, tree, and diff submitted for independent review. |
| source_checked | Inspected declarations support an example; compilation is not implied. |
| proposed_target | Intended API behavior that does not claim current implementation. |

Sentence checks do not establish full STE compliance.
Record vocabulary and technical-term decisions during the final language review.
Do not claim formal certification from this document.
